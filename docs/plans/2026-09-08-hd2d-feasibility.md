## 可行性与实现原理

现代网页可以用 WebGL 实现三维环境、像素序列帧人物、深度遮挡、阴影和受控后期处理。统一效果来自人物比例、纹理尺度、色板、光照与地面接触的一致性。大幅背景图与独立人物图的简单替换无法提供可行走三维空间。

1. 环境：用模块化三维地面、建筑、树木及道具构成可探索空间，远景可以使用背景画。
2. 人物：将一致像素规格的多方向动画贴在竖直平面上，根据镜头和移动方向选择朝向；需要受光时使用受光平面材质及适当的透明裁切、深度写入。
3. 交互：角色在地面 X/Z 坐标移动，按地面高度落脚；碰撞、遮挡、NPC 距离和镜头跟随共用世界坐标。
4. 视觉：采用稳定的斜俯视构图、接触阴影、有限主光与局部灯光；景深和泛光作为最后的增强。像素纹理采用最近邻采样，并验证镜头运动时的像素稳定性。
5. 网页：场景分章加载，重复物件合批或实例化，静态光照优先预计算；对阴影和后期提供画质档位。桌面帧率需要原型实测，不能从视频推断。中英文界面独立以清晰分辨率显示。

## 候选路线（未最终选型）

| 路线 | 优势 | 代价 |
| --- | --- | --- |
| Three.js + 现有 TypeScript / DOM | 能保留剧情、状态、关系、小游戏规则与双语系统，网页集成直接 | 需要新建三维场景、相机、碰撞与素材组织方式 |
| Godot 4 + Web 导出 | 提供场景编辑与完整游戏制作流程，接近视频的制作环境 | 需要适配/迁移已有逻辑，必须按 Compatibility 渲染验证，插件与后期不可假定原样兼容 |
| 继续 Phaser 3 的平面分层方案 | 改动较小，适合固定横向视图 | 原生为二维引擎，真实三维地图、自由镜头与复杂遮挡不适合靠其 Mesh 强行承担 |

当前可复用：剧情数据、关系与结算、辩论/军令/约克镇规则、双语文本与设置、浏览器存储。需要重做：WorldArt 场景、ChapterScene 探索视图、相机、角色素材和空间交互。

支持改方向的理由：共同空间、遮挡与光照能回应当前画面割裂的问题。需要权衡的理由：像素风本身不保证美术统一，多方向动画、模块化场景与性能仍需制作和验收。

当时的关键变量是保留横向走位、固定斜俯视探索还是自由转动镜头。用户后续明确要求每幕扩充为自由行走三维场景，并授权独立实现样例；已选择自由行走、有限俯仰和缩放、自由水平旋转。纽约街角样例的实施记录见 `2026-09-08-hd2d-sample.md`，不再等待此项澄清。
