# 0.2.0 线上 CG 缓冲排查

## 结论

主要瓶颈已确认：腾讯云实例的公网出口上限为 **3 Mbps**，而当前 CG 的平均总码率约 **10.17 Mbps**。一个观众的连续播放需求已超过整台实例的出口能力。此次采样未发现 CPU、磁盘或 Nginx 处理能力成为瓶颈。

本次仅排查并留档，没有修改线上文件、套餐或播放器。

## 视频与加载逻辑

- 文件：`public/video/opening-2026-09-11.mp4`，72,694,180 bytes（72.7 MB / 69.3 MiB）。
- 视频：H.264 / avc1，1920×1080，30 fps，57.2 秒；视频平均码率 10.013 Mbps。
- 音频：AAC，约 145 kbps，保留原视频中的音轨。
- 按媒体样本时间戳统计，视频最高一个自然秒约 20.866 Mbps；不是严格滑动窗口峰值。
- moov 在偏移 32，位于 mdat 之前，已满足文件头索引布局；无需通过 faststart 重排来修复此次带宽瓶颈。
- `OpeningFilm.ts` 只有这一种视频源，preload=auto，直接开始播放；没有低码率备选或自适应清晰度。
- `EntryScreen.ts` 在启程时同时开始 BGM、CG，并在 550 ms 入场后导入和初始化三维场景；角色图集约 3 MB，其他场景资源也会占用同一出口。此为加重因素，无法解释为单纯播放器文案误报。
- `waiting` / `stalled` 后 1.8 秒显示“正在缓冲”，12 秒提示加载慢；它反映的是媒体等待，隐藏该提示不能解决资源供给不足。

本地媒体解析细目：`artifacts/cg-buffering-media.json`。解析使用 MP4 box、stsz 和 stts 表，afinfo 交叉核对音频时长。

## 为什么只有一个访问者也卡

CG 每播放 1 秒平均消耗约 1.27 MB。3 Mbps 出口每秒理论最多传约 0.375 MB；以总文件计，57 秒 CG 理想情况下也需约 194 秒下载，实际还要与 BGM、图片及其他站点请求共享出口。月流量包 200 GB 是总量，不能抵消每秒 3 Mbps 的速度上限。

## 建议处理顺序（未实施）

1. 为网页提供限码率压缩版本，首轮以 720p、总平均约 1.5–2 Mbps 为试验目标，约 11–14 MB；同时约束峰值，保留时长、配音及现有黑场衔接。具体画质须比较样片，不能仅按文件大小验收。
2. 调整启动资源的优先级，先满足 CG 缓冲，分阶段加载非必要三维资源；保留既有音乐意图，避免不必要的下载争用。
3. 加入冷缓存、3 Mbps 限速的完整 57 秒播放验收，记录启动等待、卡顿次数和总卡顿时间。此次发布此前仅覆盖功能与资源完整性，遗漏了这项连续播放性能验收。
4. 若要支持多名玩家同时观看，将视频和大媒体放到对象存储并通过 CDN 分发，避免所有观众都从这台 3 Mbps 实例取媒体。压缩主要改善单人和低负载，不能保证多个同时播放的请求共享 3 Mbps 时仍流畅。腾讯云文档明确将视频静态资源及音视频点播列为 CDN 应用场景：[CDN 新手指引](https://cloud.tencent.com/document/product/228/43827)。

链条：高码率单一视频 → 3 Mbps 总出口饱和 → 缓冲消耗快于补充 → waiting/stalled → 播放反复等待。CPU 升级不会改变当前套餐的带宽上限。
